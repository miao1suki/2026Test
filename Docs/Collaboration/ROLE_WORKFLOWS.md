# 2026Test 角色工作卡

本文各节可以单独复制给对应成员。所有参与 Git 的成员先执行共同规则，再执行自己的角色流程。

## 所有 Git 成员的共同规则

开始任务时把下面内容与具体任务一起交给自己的 AI：

```text
先读取并严格遵守 $unity-git-branch-worker。
我的角色：ROLE
任务编号：TASK_ID
指定分支：BRANCH_NAME
目标：GOAL
允许修改：ALLOWED_PATHS
禁止修改：FORBIDDEN_PATHS
本任务由我负责编辑的 Scene/Prefab/Data：OWNED_FILES
验收条件：ACCEPTANCE
验证方式：TESTS

不要合并 main，不要创建或合并 PR，不要强推。完成后只推送自己的分支，并按 Skill 的交接格式报告。
```

共同操作顺序：

1. 在自己的独立项目副本中工作。
2. 确认 Unity 为 `6000.3.12f1`。
3. 使用 Skill 从最新 `main` 创建指定任务分支。
4. 只修改任务允许路径，不打开并保存未预约场景。
5. 在 Unity 中检查 Console 和功能结果。
6. 检查 diff，提交、推送自己的分支。
7. 向整合者交接，在收到“已合并，可以继续”前不要继续改同一文件。

关卡内容的共同规则：正式来源统一位于
`Assets/_Project/Development/Levels/<LevelId>/Authoring/Pieces/<Piece>/<Face>/<Content>.asset`。
按“关卡 / Piece / Face / 内容块”预约文件，不按策划、程序、TA 等职位建目录。
`Preview` 是生成预览，`Release` 是整合者生成的发布结果，普通成员都不要把它们作为日常编辑源。

## 工作卡 A：玩法策划

### 你的职责

- 定义玩家做什么、为什么做、成功/失败条件和反馈。
- 先写可验证的玩法说明，再要求程序实现。
- 调整已暴露的参数、ScriptableObject 数据和关卡中的设计点位。
- 在分配给你的关卡数据块中进行少量玩法点位和参数配置。
- 验收策划程序和程序交付的功能。

### 你不负责

- 不写或修改 C#、Shader、Renderer Feature。
- 不修改基础 Prefab 的内部结构；需要变体时提出需求。
- 不修改 `ProjectSettings`、`Packages`、Build Settings、渲染管线资产。
- 不修改未分配的关卡块，也不把 2D/3D 生成预览当作源文件提交。

### 每个玩法任务的流程

1. 在 `Docs/Design/Features/TASK_ID_FeatureName.md` 写清：目标、玩家输入、规则、状态、数值、边界情况、表现需求、验收步骤。
2. 与策划程序确认哪些参数要暴露给 Inspector/Data。
3. 等待策划程序提供可配置 Prefab 或组件。
4. 预约目标关卡的 Piece/Face 数据块或独立 Data 文件后进行配置和点位摆放。
5. 按验收步骤亲自试玩，记录“通过/不通过”和复现步骤。
6. 推送文档、数据和被允许的关卡数据块，交给整合者。

### 交付物

- 一份可以照着测试的玩法文档；
- 独立参数资产或点位摆放；
- 验收结果；
- 未解决的设计选择，不用含糊的“感觉不对”。

## 工作卡 B：策划程序

### 你的职责

- 把玩法文档拆成状态、组件、数据和可验证任务。
- 为玩法策划提供清晰的 Inspector 参数和安全默认值。
- 制作玩法 Prefab、ScriptableObject、Trigger/Spawner 和小型编辑器工具。
- 负责可复用玩法组件、Prefab 和被分配的关卡逻辑数据，不替关卡策划改其他空间块。
- 充当玩法策划与核心程序之间的接口人。

### 你不负责

- 不私自修改核心框架接口；需要时先与程序确认。
- 不在正式场景里写一次性、无法复用的隐藏逻辑。
- 不修改全局渲染管线、Packages 或 Build Settings。
- 不修改玩法策划正在编辑的同一个关卡数据块。

### 每个玩法任务的流程

1. 阅读玩法文档，把需求拆成：运行时逻辑、配置数据、Prefab、场景连接和测试。
2. 与程序确认公共接口；复杂底层交给程序，自己负责玩法层组合。
3. 先在 `Development/Sandbox/Systems/<SystemName>` 做最小可玩原型。
4. 把硬编码数值移入组件参数或独立 Data，写 Tooltip 和合理默认值。
5. 交付 Prefab/组件给玩法策划配置。
6. 预约目标关卡数据块后放置技术对象；使用稳定 ID，避免跨场景直接引用。
7. 用策划文档的验收步骤验证，推送并交接。

### 交付物

- 可复用组件和 Prefab；
- 策划可读的参数；
- 分配到的关卡数据块中的最小连接；
- 测试步骤和已知限制。

## 工作卡 C：关卡策划

### 你的职责

- 负责空间结构、路线、节奏、视线、探索顺序和遭遇空间。
- 维护分配给你的 `Level / Piece / Face / Geometry|Traversal` 数据块。
- 立方体地图任务只维护分配的块，不编辑其他人的 Piece/Face 数据。
- 使用模块化 Prefab 和 Variant 搭建，不复制出大量不可维护对象。
- 为玩法策划保留清晰的点位和标记，不在关卡数据中藏玩法代码。

### 你不负责

- 不修改核心程序、Shader、ProjectSettings 或渲染管线。
- 不修改未分配的数据块、生成预览和 Release 场景。
- 不随意 Unpack 公共 Prefab；确有需要时创建关卡 Variant。
- 不执行 Lighting、NavMesh、Occlusion 的最终 Bake。

### 每个关卡任务的流程

1. 从最新 `main` 开始并预约目标关卡的 Piece/Face/内容块。
2. 先做灰盒：出生点、目标点、主路线、支路、阻挡和尺度。
3. 按房间或区域小步提交，避免一次提交整个关卡的大改。
4. 使用现有环境 Prefab；缺少模块时提交独立资源需求。
5. 运行关卡，检查可达性、视线、卡死点、相机和碰撞。
6. 不处理最终灯光与 VFX，只放置规范化 Marker 或提出效果需求。
7. 推送关卡数据块和相关 Variant，交接具体 Level/Piece/Face。
8. 不提交自己生成的 2D 总拼或 3D 主场景；由整合者拉齐所有 Piece 后统一刷新并提交。

### 交付物

- 可游走的灰盒/布局；
- 关卡 Variant；
- 动线和尺度验证；
- 仍需玩法、灯光或美术处理的位置清单。

## 工作卡 D：程序

### 你的职责

- 负责核心系统、公共服务、数据流、输入、存档、加载、性能敏感模块和自动测试。
- 给策划程序提供稳定、最小且有文档的接口。
- 功能先在 `Development/Sandbox/Systems/<SystemName>` 验证，不直接改发布关卡。
- 保持模块边界清晰，避免所有功能依赖单一全局 Manager。
- 按整合者指定的 `main` SHA 生成开发包或正式候选包，并留下完整构建记录。

### 你不负责

- 不在 Release 场景或未分配的关卡数据块中调功能。
- 不顺手移动美术资源或重命名大量文件。
- 不修改渲染管线资产；渲染接口需求交给整合者。
- 不为了让 AI 编译通过而删除未知代码或放宽错误处理。

### 每个程序任务的流程

1. 确认接口、输入输出、生命周期、失败方式和性能约束。
2. 在独立功能目录中实现 Runtime 代码。
3. 能自动测试的逻辑写 EditMode/PlayMode Test；不能自动化的写最小 Test Scene。
4. 给 Inspector 字段提供清晰命名、Tooltip、默认值和必要校验。
5. 只提交任务相关脚本、测试和演示资产。
6. 确认 Unity 编译、测试和关键场景运行无新增错误。
7. 推送分支，说明公共接口、接入方法和可能影响。

### 交付物

- 可复用模块；
- 测试或最小复现场景；
- 接入说明；
- 性能和兼容性风险。

### 你作为构建执行人时

1. 从整合者获得目标平台、构建选项和完整 `main` SHA。
2. 使用干净工作区拉取 `main`，确认本地 `HEAD` 与指定 SHA 一致。
3. 不在个人功能分支或带未提交改动的工作区打包。
4. 执行构建并实际启动，完成指定 Smoke Test。
5. 记录 Unity 版本、平台、SHA、Development Build 状态、输出位置、结果和已知问题。
6. 把包和构建记录交给整合者；没有整合者确认时只能称为开发包或候选包。

## 工作卡 E：TA

### 你的职责

- 制作 Shader、材质实例、粒子/VFX Prefab 和效果参数。
- 在按效果系统命名的 Development Sandbox 中完成效果，再以 Prefab 交付。
- 只有明确分配关卡块时才放置关卡效果；只有明确授权时维护 Lighting 数据。
- 记录效果依赖的贴图、颜色空间、透明模式和性能等级。

### 由于你仍在熟悉管线，以下内容必须交给整合者

- URP Renderer Asset 和 Render Pipeline Asset；
- ScriptableRendererFeature 的全局安装和顺序；
- Universal Render Pipeline Global Settings；
- Packages、Graphics Settings、Quality Settings；
- 全局 Volume、Build Settings 和平台渲染差异；
- 最终 Lighting/NavMesh/Occlusion Bake。

### 每个效果任务的流程

1. 确认目标平台、效果触发方式、生命周期和性能预算。
2. 在 `Development/Sandbox/Systems/<EffectName>` 制作，不直接在 Release 或关卡源数据中试错。
3. Shader、Material、Texture 和 Prefab 放到对应 Rendering/Prefabs 目录。
4. 若需要管线改动，写清“需要添加什么、插入位置、输入输出和原因”，由整合者接入。
5. 用 Game View 和目标质量等级验证；检查材质丢失、粉色 Shader 和对象泄漏。
6. 预约目标关卡数据块后只放置 Prefab 实例和局部配置。
7. 推送并说明效果使用方法、可调参数和性能风险。

### 交付物

- 独立可预览的 VFX Prefab；
- Shader/材质及依赖；
- 接入说明；
- 管线变更申请；
- 性能等级和降级方案。

## 工作卡 F：程序 + TA / 整合者

### 你的职责

- 维护 Git 规则、`main`、集成分支和场景/Prefab 预约表。
- 分配任务并写明允许路径、禁止路径和验收条件。
- 负责 Bootstrap/Master、Packages、ProjectSettings、Build Settings 和 URP 全局管线。
- 辅助程序完成跨模块部分，辅助 TA 把效果正确接入管线。
- 处理冲突、烘焙数据和全项目验证；可自行打包，也可以指定主程按固定 SHA 打包。
- 管理外部美术/音频的资源导入。

### 你不应该做

- 不在成员正在使用的任务分支或同一文件中并发帮改。
- 不把未经验证的成员分支直接合入 `main`。
- 不在合并时顺手重构无关代码。
- 不因为赶时间而取消场景预约制度。

### 每次任务分配

1. 从设计目标拆出可在半天到两天完成的任务。
2. 指定负责人、分支、允许路径、文件编辑负责人、依赖、验收和测试。
3. 检查任务是否会与其他人编辑同一 Scene/Prefab/Data；有冲突就重新拆分或排期。
4. 发布任务和当前文件负责人表。

### 每次集成

1. 阅读交接和完整 diff。
2. 检查是否越权修改、缺 `.meta`、包含生成目录或大型文件。
3. 在短期 integration 分支合并，不直接在 `main` 试错。
4. Unity 完整导入、编译、测试、组合场景检查。
5. 统一处理 Render Pipeline、Build Settings、Lighting、NavMesh 和资源引用。
6. 做开发构建并实际启动。
7. 通过后更新 `main`，发布新 SHA，宣布相关文件可以由下一位成员接手。

### 每次正式打包或委托主程打包

- 确定一个已经推送到 `origin/main` 的构建基线 SHA；
- 确认目标场景和顺序；
- 清理仅开发使用的资源引用；
- 执行目标平台 Smoke Test；
- 记录 Unity 版本、平台、SHA、构建时间和已知问题；
- 包体只从干净且与指定 SHA 一致的工作区生成；
- 主程生成的正式候选包必须交给整合者验收后才能作为团队正式版本。

## 非 Git 工作卡：2D 像素美术

1. 从策划处获取尺寸、Pivot、PPU、帧数、动画命名、调色板和用途。
2. 源文件放 `AssetDrop/.../Source`，导出 PNG/Sprite Sheet 放 `Runtime`。
3. 不覆盖旧文件来表达大版本修改；增加版本号并写变更说明。
4. 在 `MANIFEST.md` 标注 PPU、Filter Mode、切片尺寸、Pivot、是否循环和透明要求。
5. 通知指定 Git 导入者，不直接把文件发给所有成员形成多个版本。

## 非 Git 工作卡：音乐音效

1. 从策划处获取用途、时长、循环点、情绪、响度和触发方式。
2. 工程与分轨放 `Source`，交付 WAV/OGG 放 `Runtime`。
3. 在 `MANIFEST.md` 标注采样率、声道、循环方式、建议音量和是否允许随机变调。
4. 音乐必须说明精确循环需求；音效变体使用统一编号。
5. 由指定 Git 导入者设置 Unity 压缩、Load Type、Loop 和 Mixer 路由。
